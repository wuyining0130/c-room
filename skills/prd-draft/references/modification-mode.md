# PRD 修改模式

当用户要求修改已有 PRD 时（如"帮我改一下 PRD"、"把角色改成 X"、"加个分类维度"、"把 review 的问题修一下"），进入修改模式而非重新走首次生成流程。

## 触发条件

**任何对已有 PRD 文件的修改都必须走完整的 M-Step 1-4 流程，没有例外。** 不存在"太小不值得走流程"的修改——哪怕只加一个待确认项，也必须升版本号和追加变更记录。

满足以下任一条件时进入修改模式：
- 用户指定了已有的 PRD 文件并要求修改
- 用户提到 prd-review 的检查报告，要求修复问题
- 用户在已生成 PRD 后给出修改意见
- 用户在对话中提出零散的修改请求（如"加个待确认项"、"把这段改一下"、"把这个信息加到 PRD 里"）
- 对话讨论中产生了需要写入 PRD 的结论或决策
- `requirements/{模块名}/prd-draft.md` 已存在，且用户的意图是修改而非重写

## M-Step 1: 读取现有 PRD 和修改来源

1. **读取当前 PRD**：读取 `requirements/{模块名}/prd-draft.md`，提取 frontmatter 中的 `version` 字段
2. **读取需求上下文**：检查 `requirements/{模块名}/prd-context.md` 是否存在。如存在，读取之前积累的用户决策和补充信息，作为本次修改的背景知识（避免与之前的决策矛盾）
3. **识别修改来源**：
   - **用户直接给出修改意见**：用户在对话中描述的变更要求
   - **prd-review 报告**：读取 `requirements/{模块名}/review/review-summary.md`；如存在可选的维度报告再按摘要引用读取，提取所有阻塞（🔴）和建议（🟡）问题
   - **混合来源**：用户给了部分意见，同时要求修复 prd-review 发现的问题

## M-Step 2: 生成修改条目清单（必须经用户确认）

**这是修改模式的核心步骤——不要跳过。** 列出所有计划修改的条目，逐条让用户确认后再动手。

输出格式：

```
📝 PRD 修改计划（当前版本：{version}）

修改来源：{用户意见 / prd-review 报告 / 混合}

---

### 计划修改项

| 编号 | 修改位置 | 修改类型 | 修改内容 | 来源 |
|------|----------|----------|----------|------|
| M-01 | 四、需求详情 > F-01 数据定义 | 修改 | 将"类型"字段的枚举值从 3 个改为 5 个 | 用户意见 |
| M-02 | 三、业务流程图 | 修改 | 补充审核驳回分支 | 用户意见 |
| M-03 | 六、待确认项 > Q-01 | 关闭 | 用户已确认方案，移入正文 | 用户意见 |
| M-04 | 四、需求详情 > F-01 验收标准 | 补充 | 添加异常场景的验收条件 | review B-01 |

### 不修改的项（说明理由）

| 跳过项 | 理由 |
|--------|------|
| 术语不统一（"签章"vs"盖章"） | 不影响功能理解，本轮不处理 |

---

以上修改是否确认？可以：
1. 全部确认，开始修改
2. 逐条调整（告诉我哪条要改或不改）
3. 补充其他修改项
```

**修改类型说明**：
- **补充**：在现有内容基础上添加缺失信息（如补充验收标准、补充异常分支）
- **修改**：改变现有内容（如修正数据模型、调整流程）
- **删除**：移除不需要的内容
- **新增**：新增此前没有的章节或功能（如新增一个 F-XX）
- **关闭**：待确认项已有结论，从待确认移入正文

### 来自 prd-review 的修改项处理规则

- 🔴 阻塞问题：全部列入修改计划，默认标记为"需修改"
- 🟡 建议问题：全部列入修改计划，默认标记为"需修改"，但用户可选择跳过
- 🔵 提示问题：列入"不修改的项"，除非用户要求处理
- 如果 review 问题的修改建议不够具体（如"建议补充边界条件"但未说是哪些边界），在修改条目中标注需要用户补充的信息

## M-Step 3: 执行修改

用户确认修改计划后，**逐条执行 Read→Edit→Verify 循环**，而不是凭记忆批量修改。

### 逐条修改流程（每个修改条目重复此循环）

```
对修改计划中的每一条 M-XX：

1. Read — 重新读取目标段落
   读取 PRD 文件中该条目涉及的章节（用 offset+limit 精确定位），
   确保看到的是当前最新内容（前面的修改可能已改变行号）

2. Edit — 基于刚读到的原文执行修改
   old_string 必须从刚才 Read 的结果中复制，不要凭记忆拼写
   修改完成后记录该条目状态为 ✅

3. Verify — 回读修改结果确认正确
   再次 Read 同一段落，检查：
   - 修改内容是否正确写入
   - 上下文是否被意外改动
   - 格式（表格对齐、列表缩进、Mermaid 语法）是否正确
   如发现问题，立即修正后再进入下一条
```

**为什么必须逐条循环**：PRD 通常 300-600 行，一次性读入全文后到执行修改时，早期内容已在 context 中衰减。凭记忆修改会导致 old_string 与实际文本不匹配（空格、换行、标点差异），造成静默跳过或改错位置。每条修改前重新 Read 目标段落，确保基于精确原文操作。

### 修改执行规则

1. **局部修改，非整篇重写**：只修改确认的条目涉及的章节，其他内容保持原样不动。使用 Edit 工具精确修改，禁止用 Write 整篇覆盖

2. **版本号递增**：更新 frontmatter 中的 `version` 字段
   - `draft-v1` → `draft-v2` → `draft-v3`（修改迭代）
   - 保持 `status: "draft"`，直到用户明确标记为终稿

3. **在文档末尾追加变更记录**：

```markdown
---

# 变更记录

| 版本 | 日期 | 变更内容 | 来源 |
|------|------|----------|------|
| draft-v2 | {日期} {时间} | M-01: 扩展类型枚举值; M-02: 补充流程图驳回分支; M-03: 关闭 Q-01; M-04: 补充 F-01 异常验收标准 | 用户意见 |
| draft-v1 | {日期} {时间} | 初始版本 | prd-draft 生成 |
```

4. **待确认项联动更新**：
   - 如果用户在修改中确认了某个待确认项的结论，将其从"待确认项"移除，结论写入正文对应位置
   - 如果修改引入了新的不确定点，新增待确认项
   - **章节自动清理**：所有待确认项关闭后删除“待确认项”章；默认假设单独判断，仍存在有效假设时保留，没有内容时才删除

5. **相关项检查（所有条目完成后）**：每个修改可能波及 PRD 其他章节。逐条回顾已完成的修改，检查是否遗漏了需要联动更新的地方。

   **常见的相关项映射**：

   | 改了什么 | 检查哪些相关项 |
   |----------|---------------|
   | 数据模型（字段增删改） | 需求详情的表单描述、验收标准中的字段引用 |
   | 流程图（新增/删除节点） | 权限矩阵是否缺少对应角色、需求详情是否缺少对应功能 |
   | 功能清单（新增/删除 F-XX） | 需求详情是否有对应章节、流程图是否覆盖 |
| 待确认项关闭 | 正文结论是否写入、是否所有待确认项已关闭（是则删除待确认项；默认假设独立判断） |
   | 角色/权限变更 | 权限矩阵、流程图中的角色标注 |
   | 验收标准变更 | 对应 F-XX 的功能范围和名称是否仍与功能清单一致 |

   **执行方式**：对每条已完成的 M-XX，查上表找到对应的相关项列，Read 这些章节确认是否需要联动修改。如果发现遗漏，追加为新的修改条目（M-XX+），走同样的 Read→Edit→Verify 循环。追加的条目在变更记录中一并记录，来源标注为"相关项检查"。

6. **全量验证（相关项检查完成后）**：从头到尾快速 Read 整个 PRD，检查：
   - 所有修改条目是否都已正确落地
   - 章节编号是否因增删内容而错乱
   - 功能清单与需求详情的 F-XX 编号、名称和范围是否一致
   - 新增或修改的 Mermaid 图是否语法正确（节点文字有双引号、判断节点有多分支）

7. **更新需求上下文文件**：将本轮修改中用户给出的决策和补充信息更新到 `requirements/{模块名}/prd-context.md`。这个文件是需求决策基线——记录所有经过确认的需求决策和业务事实，后续修改和评审都以此为基准。

   **写入判断标准**：问一句"用户本可以选别的方案吗？"——能 → 需求决策，不能 → 业务事实。

   **写入规则**：
   - 只记录用户确认的决策和事实，不记录 review 报告的内容（report 有自己的文件）
   - 决策被推翻时：更新"需求决策"中的条目为新结论，旧结论移入"变更记录"表格（不用删除线留在正文）
   - 格式简洁，每条一行，时间戳精确到秒（`YYYY-MM-DD HH:MM:SS`），带版本号
   - **时间戳必须取系统实际时间**：写入时间戳前必须先执行 `date '+%Y-%m-%d %H:%M:%S'` 获取当前时间，禁止估算或凭记忆填写。会话可能跨越数小时，估算时间会导致记录与实际严重不符
   - **每次更新必须同时写两处**：（1）在"需求决策"或"业务事实"章节追加条目；（2）在底部"变更记录"表格追加对应版本行。两处缺一不可——只加条目不加变更记录会导致版本追溯断裂，这是一个已发生过的实际问题

   **文件格式**：

   ```markdown
   # 需求上下文

   > 本文件记录需求中经过确认的决策和业务事实，作为后续修改和评审的基准。
   > 由 prd-draft 自动维护，无需手动编辑。

   ## 需求决策

   用户做出的选择——"做什么、不做什么、怎么做"。每条决策的特征是：用户本可以选择另一个方案。

   - [{日期} {时间} v2] 审核流程确认为两级审核：组长审核 → 主管审批
   - [{日期} {时间} v2] 签章类型字段改为下拉选择，不用自由输入
   - [{日期} {时间} v3] 一期支持自定义枚举（v3 修改，原为固定枚举）
   - [{日期} {时间} v3] 签章失败后需要支持手动重试，不能只有自动重试

   ## 业务事实

   客观存在的业务现状和约束条件，不是用户的选择，而是事实。

   - [{日期} {时间} v2] 合同模板最多支持 50 个签章位，超过的业务上不存在

   ## 变更记录

   | 版本 | 日期 | 变更内容 | 来源 |
   |------|------|----------|------|
   | v3 | {日期} {时间} | 一期从固定枚举改为支持自定义枚举 | 用户评审后推翻 |
   ```

## M-Step 4: 修改总结

修改完成后输出：

```
✅ PRD 已更新：{版本号}

**本次修改：**
- M-01: ✅ 已完成 — {简要说明}
- M-02: ✅ 已完成 — {简要说明}
- M-03: ✅ 已完成 — {简要说明}
- M-04: ✅ 已完成 — Q-01 已关闭，结论写入 {章节}

**剩余待确认项：** {N} 个
**需求上下文已更新：** requirements/{模块名}/prd-context.md
**建议下一步：** {根据场景选择：如果本轮修改来源包含 review 报告，建议再跑一次 prd-review 确认阻塞清零；否则建议用户自行检查或继续推进下游流程（proto-gen / tech-design）}
```

## 修改模式的原则

**先列清单再动手**：这是与首次生成模式最大的区别。首次生成时 AI 有较大自由度（在澄清基础上生成），修改时必须精确——用户已经在前一版上投入了评审精力，不能随意改动未经确认的内容。

**最小化改动**：只改用户确认的条目。不要"顺手"修改其他章节的措辞、重新排版段落、或调整未提及的内容。如果发现其他问题，列入总结的"建议"中提醒用户，而不是擅自修改。

**对话中的用户补充必须落地**：修改过程中用户可能在对话里随口补充新信息或纠正之前的说法（如"这个字段其实应该是下拉选择不是输入框"、"审核流程改成两级"）。这些信息同样是修改输入，处理规则：
- **新增信息**：追加为新的修改条目（M-XX），标注来源为"对话补充"
- **与已有内容冲突**：以用户最新表述为准覆盖旧值——用户在修改轮次中的纠正代表最新意图
- **与 review 建议冲突**：用户意见优先于 review 建议——review 是 AI 生成的检查报告，用户才是需求 owner
- **落地方式**：在当前修改批次中一并执行，不要说"下次再改"

**任何修改必须升版本**：无论是通过正式的 M-Step 流程修改，还是用户在对话中随口说"加个待确认项"、"把这段改一下"，只要对 PRD 文件做了 Edit，就必须同步完成两件事：（1）frontmatter 的 version 递增；（2）变更记录表追加一行。没有例外。这条规则之所以单独强调，是因为用户在对话中的零散修改很容易漏掉版本更新——但对于 PRD 的读者来说，版本号是判断"我看的是不是最新版"的唯一依据，漏更新会导致混乱。

**任何修改必须同步更新 prd-context.md**：与版本递增同理，每轮修改完成后必须将用户本轮给出的决策和事实追加到 `prd-context.md`。**更新时必须同时写两处：（1）在"需求决策"或"业务事实"章节追加条目；（2）在底部"变更记录"表格追加对应版本行。** 两处缺一不可——只加条目不加变更记录会导致版本追溯断裂。这条规则之所以单独强调，是因为对话会消失，但 `prd-context.md` 是需求决策基线——如果漏更新，下次修改时 AI 读不到本轮的用户决策，可能做出与之前结论矛盾的修改；prd-review 也无法正确校验 PRD 与需求决策的一致性。时间戳精确到秒（`YYYY-MM-DD HH:MM:SS`），且必须通过 `date` 命令获取实际时间，不得估算。

**保持可追溯**：每次修改都有变更记录，每个修改条目都有来源标注。这样用户回顾 PRD 演变历程时能清楚每个变化的原因。

**可选：与 prd-review 形成闭环**：如果修改来源包含 review 报告，修改后建议再跑一次 prd-review 确认阻塞清零。但很多时候用户只是在迭代自己的想法，不需要每次都过 review。典型路径：

```
# 路径 A：用户直接迭代（最常见）
prd-draft(v1) → 用户想改 → 修改模式(v2) → 继续推进

# 路径 B：review 驱动修复
prd-draft(v1) → prd-review → 发现阻塞 → 修改模式(v2) → prd-review → 阻塞清零
```
