#### 标题编号规则

PRD 各章节标题必须带序号，方便在评审和沟通时精确引用（如"请看 3.2 的验收标准"）。编号规则：

- 文档主标题 `# {需求标题}` 不计入章节编号；其后的 PRD 正文章节从 `# 一、...` 开始
- 一级标题（`#`）使用中文数字：一、二、三、……
- 二级标题（`##`）使用阿拉伯数字：1.1、1.2、2.1、……
- 三级标题（`###`）使用阿拉伯数字：1.1.1、1.1.2、……
- 功能编号（F-01、F-02）保留在标题中，与章节编号并用，如 `## 4.1 F-01: 盖章模式配置`

示例：
```
# 一、需求背景
## 1.1 背景与目标
## 1.2 需求范围
# 二、功能清单
# 三、业务流程图
# 四、需求详情
## 4.1 F-01: xxx
## 4.2 F-02: xxx
# 五、权限管理
# 六、待确认项
# 七、默认假设
```

#### 文档生成原则

- **产品导向，业务方可读**：PRD 的读者不只是开发和测试，还包括业务方、产品负责人、法务等非技术角色。全文必须使用产品语言和业务语言，让不懂代码的人也能无障碍阅读。具体要求：
  - **禁止出现代码实现细节**：不写类名（如 `SealHandlerServiceImpl`）、方法名（如 `genSealStrategyJson()`）、表名（如 `t_e_seal_strategy`）、字段名（如 `FstrSealLx`）、包名、注解名等
  - **用业务语言描述功能行为**：写"签章服务根据 PDF 实际页数，自动在每页相同位置生成签章"，而不是"ESealStrategyService 动态生成 N 条签章策略 JSON"
  - **数据模型用业务概念命名**：写"签章策略"而不是"ESealStrategy"，写"签章配置"而不是"ContractBody"，字段说明用中文业务含义
  - **流程图用角色/系统名称**：泳道标签写"运营后台"、"签章服务"、"合同生成引擎"，而不是写服务代号（如 `atm_api`、`e_seal_srv`）
  - **验收标准描述可观测的业务结果**：写"生成的 PDF 每页都有签章"，而不是"SealHandlerServiceImpl 识别 PER_PAGE 类型后调用动态策略生成"
  - **错误处理用用户视角**：写"签章失败时提示具体原因，合同进入重试流程"，而不是"failReason 记录到 t_e_contract 表"
  - coding-knowledge 中的技术细节可以帮你理解系统能力、判断需求可行性、设计合理的功能边界，但输出到 PRD 时必须翻译为产品语言。技术实现细节（改哪个服务、调哪个接口、数据库怎么改）留给下游的 tech-design skill
- **"与 XX 保持一致"不展开**：如果用户说"与某功能保持一致"但未在澄清阶段确认具体范围，PRD 中只写"与 XX 功能保持一致（具体范围见待确认项）"，不要自行发挥描述该功能的细节
- **已确认的内容写实**：基于澄清对话中用户确认的信息，忠实还原
- **待确认的内容标注**：如某个功能包含关键待确认点，可在功能名称或描述中标 `⚠️` 提醒，并在文末的"待确认项"中详细列出；不要为功能清单新增"状态"列
- **默认假设明示**：不要悄悄假设，所有推断都在"默认假设"章节中列出依据
- **引用知识库**：在需求详情的数据定义、权限管理等模块中，用业务语言引用知识库中的相关信息（如"现有签章策略配置"），帮助读者理解新需求与现有系统的关系，但不暴露底层表名或代码结构
- **不设置泛化的输入/输出/约束栏位**：输入方式写入交互说明，产出结果写入功能描述或验收标准，业务限制写入“业务规则与边界”。不要为了模板完整把同一事实拆到多个泛化栏位
- **有序列表每项必须独占一行**：凡是用 `1. 2. 3.` 编号的列表（如"本次包含"、"本次不含"、验收标准等），每个编号必须换行，严禁将多个编号挤在同一行

#### 章节分工与去重原则

PRD 各章节有明确的信息归属，**同一信息只在归属章节完整描述，其他章节引用而非复述**。

#### 1.1 背景与目标 与 1.2 需求范围的定位区分

这两个小节容易写成同一组功能点的重复。它们的定位不同：

- **1.1 背景与目标**：回答"为什么要做、做成后业务上会变成什么样"。背景写客观现状和核心痛点；目标与收益可以合并表达，写可感知的业务结果、用户行为变化和核心受益角色。不要在目标里逐条列交付物名称，也不要把"本次包含"的范围句改写一遍。
- **1.2 需求范围**：回答"本期做到哪些能力边界、不做哪些边界"。粒度是能力域或业务边界，如"统一检索能力"、"运营侧下载闭环"、"历史数据覆盖"，不是 F-XX 功能清单的复制。

**判断标准**：如果 1.1 的目标和 1.2 的"本次包含"可以逐条对上，或者只是把"建立/重构/提供"换成同义词，说明两节重复了。应把 1.1 改成业务结果，把 1.2 改成能力边界。

**精简要求**：1.1 是摘要，不是需求决策清单。背景通常 2-3 条，目标与收益通常 2-3 条；只有当不同角色的收益会影响需求边界时，才单独展开角色收益，否则合并在目标与收益中表达。

**示例：**

```markdown
## 1.1 背景与目标

**目标与收益：**
- 用户可以通过一个入口查全相关合同，减少反复试错和人工询问。
- 法务和业务侧使用同一套分类口径解释合同筛选和下载结果。

## 1.2 需求范围

**本次包含：**
1. 统一检索能力：围绕 UID、订单、标的聚合相关合同。
2. 下载闭环能力：覆盖查询预览、勾选确认、审批和异步打包。
```

#### 1.2 需求范围与功能清单的定位区分

这两个章节容易写成同一内容的重复。它们的定位不同：

- **1.2 需求范围（"本次包含"）**：回答"做哪几件事"，粒度是**业务目标/能力**级别，面向产品经理和业务方对齐预期。通常 2-4 条，每条是一个可独立理解的业务目标。例如："建立合同模板的分类标签体系"、"提供按分类 tag 检索合同的能力"。
- **二、功能清单**：回答"拆成几个用户可感知、测试可验收的产品功能模块"，粒度是**产品能力闭环**级别，而不是开发任务或技术实现步骤。每条对应第四章一个完整的需求详情块（F-01、F-02...）。常见数量为 3-6 条；只有当用户角色、主流程、验收口径明显不同，才拆成独立 F-XX。

**判断标准**：如果"本次包含"和功能清单写出来几乎一样（条目数相同、描述相似），说明"本次包含"写得太细了——应该合并为更宏观的业务目标描述。

| 信息类型 | 归属章节（完整描述） | 其他章节（引用方式） |
|----------|---------------------|---------------------|
| 功能的输入/输出/约束 | 四、需求详情（每个 F-XX 内按需保留，仅有补充价值时写） | 二、功能清单保留编号、名称、描述（场景+简介）、优先级，作为索引表 |
| 需求范围 | 一、需求背景 > 1.2 | 二、功能清单不重复列举范围，只列功能条目 |
| 业务流程 | 三、业务流程图 | 四、需求详情中只写该功能特有的交互步骤，不重复整体流程 |
| 角色权限 | 五、权限管理 | 四、需求详情中不逐功能重复角色限制，仅在权限矩阵中统一定义 |
| 实体字段定义 | 四、需求详情 > 对应 F-XX 的数据定义 | 同一 F-XX 其他段落引用"见本功能数据定义"，不重复列字段 |
| 错误处理 | 四、需求详情（每个 F-XX 内） | 三、流程图中异常分支只标节点名，详细提示文案在需求详情中 |

**具体执行**：

1. **功能清单是产品能力索引表**：功能清单（第二章）保留编号、功能名称、描述、优先级四列。描述列侧重"谁在什么场景下完成什么产品能力"，与需求详情中的功能描述（侧重"做什么"）区分开。不含状态列（待确认信息放待确认项章节管理）
2. **避免按实现步骤过度拆分**：不要把后台索引写入、关联链路补齐、历史数据刷新、页面查询、列表勾选、异步任务提交等实现环节机械拆成多个 F-XX。若这些环节共同服务于同一个用户可验收能力，应合并为一个 F-XX，并在需求详情中用"能力范围 / 处理规则 / 验收标准"展开。
3. **流程图与交互流程互补不重叠**：第三章的业务流程图描述端到端全局流程（跨角色/跨系统），第四章的交互流程只描述该功能特有的页面级正常操作步骤。失败分支只写简短场景名（如“保存失败”），完整提示与恢复方式只写在错误处理中。如果某功能的交互就是全局流程的一个子集且无额外细节，写"交互流程见业务流程图第 X 步"即可
4. **数据定义按功能嵌入**：如某个 F-XX 涉及新数据实体或结果字段，在该 F-XX 的"数据定义"小节中定义一次；同一功能的表单描述、验收标准如需提及字段，引用"见本功能数据定义"，不复制字段表格
5. **权限集中管理**：第五章权限矩阵是权限的唯一归属地。第四章不逐功能写"仅 XX 角色可操作"，如需强调特殊权限逻辑（如数据行级权限），在第五章补充说明

#### 单个功能点的信息归属与语义去重

一个业务事实在同一个 F-XX 中应有一个主要归属。判断两条内容是否冗余，不看措辞是否相同，而看第二次出现是否给读者增加了新的用途：新的操作信息、新的提示与恢复方式，或可执行的测试场景和可观察结果。没有新增用途的同义改写应删除。

| 小节 | 唯一职责 | 不应出现 |
|------|----------|----------|
| 功能描述 | 用一句话说明用户或系统获得什么核心能力、产生什么业务结果 | 操作步骤、字段限制、异常文案、测试步骤 |
| 交互说明/流程 | 正常路径中用户做什么、页面如何响应 | 详细业务限制、完整错误文案、对正常流程的验收式复述 |
| 业务规则与边界 | 正常业务规则及适用边界，如必填、长度、唯一性、数量、状态和数据范围 | 错误提示、恢复动作、“校验正确”之类验收结论 |
| 错误处理 | 规则不满足或执行失败时的用户提示、数据状态和恢复方式 | 再次解释为什么受限、重复完整规则、重复正常流程 |
| 验收标准 | 从测试视角给出场景、关键操作和可观察结果，证明需求成立 | 把功能描述、规则或错误文案换词重写一遍 |

验收标准可以包含理解测试所需的最少上下文，但不能概括已经完整写在交互流程中的正常闭环。若交互流程已定义“提交 → 生成任务 → 查看状态 → 下载”，验收标准不要再写“提交后可追踪至下载”，而应写成“提交一次申请后，任务中心仅生成一条对应记录；任务完成时下载入口可用，文件可以正常打开”。这段话增加了唯一性和可用性判据，测试人员无需跳转解码。

#### 内部去重台账与最终文档分离

生成时可以在思考或临时草稿中给规则、异常、验收分配编号，用来检查覆盖关系。但编号是写作工具，不是产品文档内容。最终交付前必须删除以下形式：

- I-01、B-01、E-01、AC-01 等原子编号
- “满足 B-01”“触发 E-02”“按 I-01 执行”等机器式引用
- 需要读者在多个小节之间来回查编号才能理解的句子

最终 PRD 使用自然承接：错误处理用简短场景名，如“分类名称重复时”；验收标准保留必要的场景上下文，如“输入已存在的分类名称并保存时”，但提示全文只在错误处理中写一次。

对“规则被违反”的场景按阅读目的拆分，不使用外显编号：

```markdown
**业务规则与边界：**
1. 分类名称在同一租户内不可重复。

**错误处理：**
1. 分类名称重复时：保留已填内容并提示“分类名称已存在，请修改后重试”。

**验收标准：**
1. 输入有效且未被使用的名称后，分类创建成功，列表仅新增一条对应记录。
2. 输入已存在的名称并保存时，系统阻止创建，输入内容保持不变；提示文案符合错误处理定义。
```

不要写成：功能描述说“名称不可重复”，规则再写“同租户名称唯一”，错误处理再解释“重名不能保存”，验收标准最后写“系统应校验名称不重复”。错误处理和验收可以再次提到“重名”作为必要场景，但分别只补充用户反馈和测试结果。

**按需保留小节**：每个 F-XX 必须有功能描述和验收标准；交互说明、交互流程、业务规则与边界、错误处理、数据定义仅在有独立信息时保留。没有内容时删除标题，不写“无”“不涉及”“按系统统一处理”。模板完整不等于每个栏位都必须填满。

#### 每个功能必须有验收标准（无例外）

每个 F-XX 功能的需求详情中**必须包含「验收标准」小节**，即使功能描述为"与现有功能一致"或"复用 C 端交互"。这是因为测试团队需要据此设计测试用例——"与 C 端一致"不是可执行的验收条件。

**验收标准与其他小节的去重原则**：验收标准不是需求正文的复述，而是对需求的验证视图。优先写正常闭环结果、跨功能联动、状态变化和正文无法直接看出的质量结果。覆盖已有规则或错误处理时，用最短的自然场景名称承接，不复制完整规则和提示文案：
- **交互说明**：如交互说明写了"按模块独立发布"，验收标准不再写"发布仅影响对应模块"
- **配置项表**：如配置项表已写明"支持多变体（|||分隔）、支持插入变量"，验收标准不再写"话术支持多变体输入"
- **边界条件**：如边界条件写了"完结节点不允许有出边"，验收标准不再重复

典型的验收标准聚焦于：
- **正常闭环结果**：完成操作后用户可以观察到的最终业务结果
- **跨功能联动**：双向同步、数据一致性、模块间隔离
- **状态变化**：操作前后的状态流转（如发布后按钮隐藏，再编辑后按钮重新出现）
- **不可见的质量要求**：视觉区分、变量注入生效、数据自动保存等

如果一条验收标准只是交互说明某一条的复述（如交互说明写了"左右分栏布局"，验收标准又写"左右分栏布局展示正确"），则应删除。

#### 成稿后的逐功能去重检查

写完 PRD 后，逐个 F-XX 静默执行以下检查，再向用户交付：

1. 把功能描述、交互、业务规则与边界、错误处理、验收标准拆成最小语义条目。
2. 为每条提取“触发条件”和“行为/结果”；两项都相同即判为重复，不因措辞不同而保留。
3. 按本节职责表选择主要正文归属；其他位置没有新增阅读价值就删除。确需建立测试或异常关联时，用自然语言给出最少场景上下文，并补充正文中没有的可观测判据。
4. 删除没有独立信息的小节，以及“无”“不涉及”“符合预期”“正确展示”等无新增信息的占位句。
5. 检查去重没有造成信息丢失：每条已确认的规则、异常反馈和关键业务结果仍至少保留一次。

6. 搜索并删除 I-XX、B-XX、E-XX、AC-XX 等内部编号和机器式引用，确保每条内容无需跳转解码即可理解。

交付门槛：同一事实的再次出现必须承担不同阅读目的；验收标准仍覆盖正常主路径和关键异常；最终文档自然可读，不暴露内部去重机制。

对于复用型功能，验收标准应明确：
- 复用的具体行为（如"支持新增、删除相似问句，IM/IVR 独立管理"）
- 数据范围差异（如"仅展示坐席辅助 FAQ 类型的数据，不与 C 端 FAQ 交叉"）
- 与被复用功能的差异点（如有）

#### 配置项使用字段级表格描述

当需求涉及可配置的表单/面板（如节点配置面板、管理侧面板等），必须使用字段级表格描述每个配置项，而不是用要点列表笼统带过。表格格式：

```markdown
**配置项：**

| 分组 | 字段 | 控件类型 | 必填 | 选项/说明 |
|------|------|---------|------|----------|
| 基础信息 | 节点名称 | 输入框 | 是 | 最长100字符 |
| 对话控制 | 是否可打断 | 开关 | 否 | 默认关闭。开启后用户可在播报时打断 |
| 挂断配置 | 归档类型 | 下拉框 | 是 | 正常归档 / 异常归档 / 无需归档 |
```

各列说明：
- **分组**：字段在配置面板中的分组归属（如"基础信息"、"话术配置"）；如无分组用"—"
- **字段**：字段名称，与数据模型保持一致
- **控件类型**：输入框、文本域、下拉框、开关、只读标签、映射表、多行文本域等
- **必填**：是/否
- **选项/说明**：下拉框的可选值、输入框的格式约束、字段的业务含义说明

这样做的原因是：要点列表容易遗漏字段的控件类型和约束，开发需要反复追问"这个字段是下拉还是输入"、"必填还是选填"。字段级表格让 PRD 直接可落地开发。

#### Mermaid 节点文字必须用双引号包裹

所有 Mermaid 节点的文字内容**一律用双引号包裹**，避免特殊字符导致渲染失败。以下字符在 Mermaid 中有保留含义，不加引号会导致解析错误：
- `→`（全角箭头）— 与 Mermaid 箭头语法混淆
- `:`（冒号）— Mermaid 中用于标签定义
- `(` `)` `{` `}` `[` `]` — Mermaid 中用于节点形状定义

正确写法：`A["提示：请先解除应用绑定"]`、`B{"校验通过?"}`
错误写法：`A[提示:请先解除应用绑定]`、`G[勾选 → 批量操作]`

同时避免在节点文字中使用 `→`，改用文字描述（如"勾选后批量操作"代替"勾选 → 批量操作"）。

#### 流程图必须覆盖异常分支

业务流程图生成规则：
- 每个判断节点必须有至少两个分支（正常路径 + 异常/失败路径）
- 涉及异步操作（MQ 同步、ES 写入、外部服务调用）的节点，必须标注失败分支
- 失败分支只需标明简短异常场景；页面提示、状态回滚、手动重试等详情只在对应功能的错误处理中写一次
- 这样做的原因是：缺少异常分支的流程图会导致测试团队遗漏异常场景的用例设计，开发也容易忽略错误处理逻辑

#### 跨系统流程必须使用泳道图

当业务流程涉及多个系统/服务（如前端、后端、MQ、ES、第三方服务）时，必须使用 Mermaid `subgraph` 按系统拆分为泳道图，而不是把所有节点平铺在一张 flowchart 里。这样做的好处是：
- 开发能直观看到每个服务的职责边界
- 技术方案阶段可以直接据此拆分改动范围
- 测试能据此设计跨服务集成测试用例

判断标准：如果流程中的节点分属不同的仓库/服务/系统（从知识库 `architecture.md` 可知），就应该用泳道图。

#### 多步骤交互必须补充交互流程

当需求详情中的功能涉及多步骤交互（分步表单、弹窗确认链、先选择再配置、状态流转操作等），必须在「交互说明」之后补充「交互流程」小节，用步骤列表或 Mermaid 图描述完整的操作序列。每一步需说明：
- 触发条件（用户点击什么 / 满足什么条件）
- 页面响应（跳转、弹窗、区域刷新）
- 分支处理（成功路径与取消后的后续行为；失败路径只写场景名，详情见错误处理）

这样做的原因是：纯文字的「交互说明」容易遗漏步骤间的衔接逻辑（如"取消后回到哪个状态"、"保存失败后表单数据是否保留"），导致开发自行决定、测试无据可依。

#### 从知识库提取枚举值和菜单路径

生成 PRD 时，应主动从知识库中提取以下信息写入文档：
- `system-overview.md` 中的枚举值列表（渠道类型、状态值、配置选项等），写入对应功能的需求详情
- `system-overview.md` 中的菜单层级路径（如"知识库 > 坐席辅助知识库 > FAQ管理"），写入页面结构章节
- 如果前端使用动态路由（从 architecture.md 可知），输出菜单路径而非路由路径
- `data-model.md` 中相关实体的现有枚举值定义，写入对应功能的数据定义或需求详情
- 这些信息知识库中已有，不写入 PRD 会导致下游测试和开发反复去知识库查找

#### 错误处理必须包含具体提示文案

需求详情中的"错误处理"部分，必须给出用户可见的具体提示文案，而不是只描述场景。例如：
- 好的写法：`删除已绑定应用的机器人类型时 → 提示"该机器人类型已绑定应用{应用名}，请先解除绑定后再删除"`
- 不好的写法：`删除已关联应用的类型时不能删除`
