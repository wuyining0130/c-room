## 产物路径解析

在文件查找、新建／修改判定和质量门禁之前，先读取 `../conventions/SKILL.md` 第 5.1 节。新建产物使用中文标准名称，评审报告、代码审查报告与交互原型直接放在 `requirements/{模块名}/` 下；既有文件沿用解析后的实际路径。正文和模板中的标准路径均受该兼容规则约束，下游引用记录实际读取文件及版本。

## Purpose

检查 PRD 的完整性、可验收性及跨章节一致性，结合可用知识库核对系统现状，输出分级问题和修改建议。

## 输入

用户提供 PRD 文件路径（Markdown 格式）。PRD 通常包含需求背景、功能清单、业务流程图、需求详情、权限管理等章节；数据定义嵌入对应 F-XX，待确认项和默认假设按实际内容检查。

## 工作流程

### Step 1: 读取 PRD 和知识库

1. 读取用户指定的 PRD 文件，提取 YAML frontmatter 中的 `version` 和 `module` 字段（如有），用于报告中标注检查的版本
   - 如 `mode: mini`，按轻量需求检查：背景是否说明原因、每个 F-XX 是否具体且可测试；不要求补功能清单、流程图、权限等完整章节
2. 根据 PRD 文件所在目录确定业务模块名（通常是 `requirements/{模块名}/{模块名}需求文档.md`），唯一必需报告输出为同目录下的 `{模块名}需求评审报告.md`
3. 按 conventions Section 3.5 的优先级查找 PRD 知识库。
4. 如果存在知识库，读取以下文件用于交叉校验：
   - `system-overview.md` — 校验功能是否重复、权限体系一致性
   - `business-flows.md` — 校验业务流程衔接
   - `glossary.md` — 校验术语一致性（读"业务定义"部分）
5. 如果知识库不存在，仅做文档自身完整性检查，在报告中提示建议先运行 `coding-knowledge-init`
6. 检查 PRD 同目录下是否存在 `{模块名}需求上下文.md`（需求决策基线）。如存在，读取其中的"需求决策"和"业务事实"，用于 2.7 需求上下文一致性校验

### Step 2: 逐模块检查

对每个模块按以下维度审查。每发现一个问题，记录问题描述、严重程度、修改建议、知识库依据（如有）。报告使用产品语言，技术证据须转化为业务影响与可操作建议。

**特别注意跨模块一致性**——功能清单里有的功能，需求详情里必须有对应描述；业务流程图里的角色，权限管理里必须有定义。这类交叉不一致往往是最有价值的发现。

#### 2.1 需求背景（含目标、收益、范围）

- 背景是否清晰（需求从哪来？谁提出的？什么场景触发？）
- 问题是否有依据（数据、用户反馈、竞品分析，而不是"我觉得"）
- 业务目标是否量化（转化率提升 X%、效率提升 X 分钟等可衡量指标）
- 用户收益是否具体（对谁有什么好处，有场景说明）
- 范围是否界定（本次做什么、不做什么）
- 优先级是否合理（投入产出比是否说得通）

#### 2.2 功能清单

- 功能是否完整（结合业务流程看，有没有遗漏）
- 优先级是否标注（P0/P1/P2 或类似标记）
- 与现有功能是否重复（对照知识库 `system-overview.md` 的"功能清单"章节）
- 功能边界是否清晰（不会产生歧义）

#### 2.3 业务流程图

如果需求没有多步骤、跨角色或状态流转，允许省略并跳过本维度；不要要求为了结构完整补流程图。

- 主流程是否完整（从起点到终点，正常路径走得通）
- 异常分支是否覆盖（失败、超时、取消、驳回等）
- 角色是否标注（每个操作节点由谁执行）
- 与现有流程是否衔接（对照知识库 `business-flows.md`）
- 状态流转是否完整（所有可能的状态转换）
- 判断分支与需求详情一致（流程图中每个判断分支的规则是否与对应 F-XX 需求详情中的约束描述一致，如流程图允许删除上线视频但 F-XX 约束说仅下线可删除，则标 🔴）

#### 2.4 数据定义（按实际内容检查）

- 扫描各 F-XX 内的“数据定义”、字段配置和业务对象说明；PRD 没有新增/修改数据实体时，跳过本维度，不要求补空章节
- 实体是否完整（涉及新增或修改的业务对象均有对应定义）
- 字段是否充分（类型、长度、约束是否定义清楚）
- 关系是否明确（一对多、多对多等关联关系）
- 与现有模型是否冲突（对照知识库 `data-model.md`）
- 枚举值是否列全（状态、类型等字段的可选值）

#### 2.5 需求详情

- 交互说明是否清晰（页面布局、操作流程、反馈方式）
- 验收标准是否可测（可验证的验收条件）
- 有明确业务边界时是否定义（最大值、最小值、空值、特殊字符）；没有独立边界时不得要求补“无”占位
- 存在需要用户反馈或恢复动作的错误时是否定义；没有独立错误场景时允许省略
- **功能内去重检查**：功能描述、交互、业务规则、错误处理、验收标准是否存在没有新增阅读价值的同义复述
- **人类可读性检查**：是否泄漏 I-XX/B-XX/E-XX/AC-XX 等内部写作编号，是否要求读者跨小节解码才能理解；发现时标为 🟡 建议
- **验收视角检查**：验收标准可以保留最少场景上下文，但必须提供可执行步骤或可观察结果，不能只把规则改写成“系统应正确校验”
- 术语是否一致（对照知识库 `glossary.md` 的"业务定义"部分）
- **产品导向检查**：PRD 全文是否包含代码实现细节（类名、方法名、表名、字段名、服务代号等）。PRD 的读者包括业务方和法务，不能出现 `SealHandlerServiceImpl`、`t_e_contract`、`genSealStrategyJson()` 这类代码层面的内容。如果发现，标为"建议"并给出产品语言的替换写法

#### 2.6 权限管理

如果需求不涉及权限变化且正文没有特殊权限要求，允许省略并跳过本维度。

- 角色是否完整（涉及的所有用户角色列全）
- 权限矩阵是否清晰（每个角色对每个功能的操作权限：查看/编辑/删除/审批）
- 与现有角色体系是否一致（对照知识库 `system-overview.md` 的"角色与权限"章节）
- 数据权限是否考虑（数据可见范围：只看自己的 vs 看全部）
- 特殊场景是否覆盖（角色变更、权限继承、临时授权）

#### 2.7 需求上下文一致性（双向校验）

如果 PRD 同目录下存在 `{模块名}需求上下文.md`（由 prd-draft 自动生成的需求决策基线），执行双向一致性校验。prd-context 中的"需求决策"是用户做出的选择（本可以选别的方案），"业务事实"是客观约束——两者的校验逻辑不同。

**Context → PRD 方向（决策是否落地、事实是否矛盾）：**
- **需求决策**：逐条检查是否在 PRD 正文中体现（功能清单、需求详情中的数据定义、流程图等章节）
  - 决策在 PRD 中找不到对应描述 → 🔴 阻塞："需求决策未落地"
  - 决策与 PRD 描述矛盾（如 context 说"两级审核"但 PRD 写了"一级审核"）→ 🔴 阻塞："PRD 与需求决策矛盾"
- **业务事实**：检查 PRD 是否与事实矛盾（不要求每条都出现在正文中）
  - 已确认的硬约束事实与 PRD 矛盾，且会改变业务行为、数据口径或验收结果 → 🔴 阻塞
  - PRD 仅未复述不影响实现的背景事实 → 不要求写入正文

**PRD → Context 方向（重要决策是否收录）：**
- 扫描 PRD 中的关键决策点：数据定义的核心字段设计、流程分支规则、权限矩阵特殊限制、验收标准量化指标
- 判断标准：这个决策点"用户本可以选别的方案吗？"——如果是，且 context 中没有对应记录，标为 🟡 建议："建议将此决策补录到 {模块名}需求上下文.md"
- 这个方向不标阻塞，因为 context 可能是早期版本、还没来得及同步

**不存在 {模块名}需求上下文.md 时：**
- 标为 🟡 建议："建议通过 prd-draft 生成 {模块名}需求上下文.md 作为需求决策基线，便于后续修改和评审时追溯用户确认的决策"
- 不阻塞，因为手写的 PRD 可能没有走 prd-draft 流程

#### 2.8 待确认项（仅当章节存在时检查）

如果 PRD 中不存在待确认项章节（已定稿清理），跳过此维度。存在时检查：

- 待确认项是否标注了影响范围（影响哪些功能或章节）
- 待确认项是否给出了倾向性建议方案（而不是完全开放式问题）
- 待确认项如果影响验收标准设计（如枚举值列表、交互模式选择），应标为 🟡 建议——因为测试团队无法基于开放式待确认项设计测试用例
- 待确认项数量是否合理（过多说明澄清不充分，过少可能遗漏了真正的模糊点）
- 功能清单中标记为"待确认"的功能，是否在此章节有对应条目

#### 2.9 默认假设（仅当章节存在时检查）

如果 PRD 中不存在默认假设章节（已定稿清理），跳过此维度。存在时检查：

- 假设是否有依据（基于行业惯例、现有系统做法、还是无依据猜测）
- 假设是否与知识库中的现有做法矛盾（对照知识库验证）
- 假设是否影响验收标准（如果某个假设不成立，验收标准是否需要调整）
- 假设是否应该升级为待确认项（如果假设的影响范围大或不确定性高）

### Step 3: 生成检查报告

在 PRD 文件所在的业务模块目录下输出完整汇总报告：

```
requirements/{模块名}/
├── {模块名}需求文档.md                    ← prd-draft 产出的草稿
└── {模块名}需求评审报告.md           ← 本 skill 产出的完整报告
```

每次运行报告完全覆盖上一次（非增量追加）。

#### 报告格式

生成报告时读取 `references/review-report-template.md`。按实际适用维度输出，问题编号全局递增；保留 PRD 来源与版本、分级问题、跨章节冲突及修改建议。

#### 问题严重程度定义

准确分级是这个 skill 的核心价值——过多"阻塞"让作者疲于应付，过少起不到把关作用。

**prd-review 特有的判断标准**：

| 级别 | 判断标准 |
|------|----------|
| 🔴 阻塞 | 开发看到会说"这块怎么做？我得找 PM 确认" |
| 🟡 建议 | 开发看到会说"大概知道怎么做，但细节不太确定" |
| 🔵 提示 | 开发不会有疑惑，只是"写得更规范就更好了" |

典型阻塞场景：功能清单缺核心功能、没有验收标准、关键数据定义与现有系统矛盾、权限遗漏关键角色。

典型建议场景：异常流程未覆盖、边界条件未定义、术语不一致、优先级未标注。

典型提示场景：措辞可更清晰、建议补充示例图、建议统一格式。

### Step 4: 输出总结

检查完成后，在对话中告知用户：
1. 检查了哪些模块
2. 各级问题数量
3. 是否可交付开发
4. 报告文件位置（`requirements/{模块名}/{模块名}需求评审报告.md`）
5. 如有阻塞问题，列出前 3 个最关键的

## 知识库交叉校验做法

交叉校验是语义层面的对比，不是简单关键词匹配：

**数据定义冲突：** 从各 F-XX 提取实体名和字段名 → 在 `data-model.md` 中查找同名或语义相近实体 → 对比字段定义和关系是否矛盾

**权限一致性：** 从 PRD 提取角色名 → 在 `system-overview.md` 的"角色与权限"章节中查找 → 新角色标"建议"确认是否需新增 → 已有角色检查新权限是否与现有矩阵矛盾

**流程衔接：** 从 PRD 识别起始/结束节点 → 在 `business-flows.md` 中查找 → 检查输入是否是现有流程的输出 → 检查是否影响现有步骤

**功能重复：** 从 PRD 提取功能描述 → 在 `system-overview.md` 的"功能清单"章节中搜索语义相似功能 → 高度相似标"建议"确认是增强还是新建

**术语一致：** 在 PRD 全文中识别业务术语 → 对照 `glossary.md` 的"业务定义"部分 → 同一概念用了不同名称标为"建议"

注意：知识库中的信息反映的是现有系统状态，PRD 中与现有系统不同不一定是"错误"——可能是有意的升级或改造。遇到不一致时，标为"建议"并说明差异，让作者确认是否有意为之，而不是直接标"阻塞"。

## 迭代使用

业务修改后复查受影响的问题；完整复评时覆盖已有报告并记录当前 PRD 版本。

## 与其他 skill 的关系

- **前置**：`coding-knowledge-init` 生成的 `coding-knowledge/business/` 提供交叉校验的依据
- **输入**：PRD 文档（可由 `prd-draft` 或其他方式产出）
- **输出**：检查报告（`requirements/{模块名}/{模块名}需求评审报告.md`），可被 prd-draft 修改模式直接读取
- **约定**：详见 `conventions` skill 中的目录规范
