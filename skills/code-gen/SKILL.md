## 产物路径解析

在文件查找、新建／修改判定和质量门禁之前，先读取 `../conventions/SKILL.md` 第 5.1 节。新建产物使用中文标准名称，评审报告、代码审查报告与交互原型直接放在 `requirements/{模块名}/` 下；既有文件沿用解析后的实际路径。正文和模板中的标准路径均受该兼容规则约束，下游引用记录实际读取文件及版本。

## Purpose

根据已确认的技术方案、PRD 和原型，在目标仓库生成完整业务实现，并核对实际变更和验证结果。

## 输入

- `requirements/{模块名}/{模块名}技术方案.md`（主要输入，包含接口设计、DDL、任务拆解、改动范围）
- `requirements/{模块名}/{模块名}需求文档.md`（验收标准、业务规则、边界条件）
- `requirements/{模块名}/{模块名}交互原型.html`（前端页面结构参考）
- `coding-knowledge/`（**核心参考**——代码风格、架构模式、符号索引、调用链、DDL 模式、代码规范）
- 目标代码仓库路径（用户指定，或从 tech-design 的改动范围中提取）

## 工作流程

### Phase 0: 读取输入、构建上下文

#### 0.1 读取 {模块名}技术方案.md

提取以下信息，作为后续生成的权威源：
- 改动影响范围（涉及哪些仓库、哪些文件需要新增/修改）
- 接口设计（API 清单、请求参数、响应结构、错误码）
- 数据库变更（DDL）
- 开发任务拆解（T-01, T-02... 含依赖关系）
- 交互时序图（服务间调用关系）
- 复用接口参数说明（区分参数和行为差异）

#### 0.2 读取 {模块名}需求文档.md

提取以下信息，用于确保业务逻辑完整：
- 功能清单和验收标准（确保生成的代码覆盖每个功能点）
- 业务规则和边界条件（确保代码中有相应的校验逻辑）
- 错误处理要求（具体的错误提示文案）

#### 0.3 深度读取 coding-knowledge（核心步骤）

按 conventions Section 7 的三层策略读取（infra → repos → business）。code-gen 的侧重点是**学习编码模式**——不仅看签名，更要从中找到同类型参考文件的完整源码。

#### 0.4 风格学习（关键步骤）

从 symbols.md 中定位 **2-3 个同类型的现有实现文件**，用 Read 工具读取完整源码。目的是学习项目的编码模式，而非仅看签名。

具体做法：

| 待生成的代码层 | 从 symbols.md 找到的参考对象 | 学习要点 |
|---------------|--------------------------|---------|
| Entity/Model | 同仓库现有的 Entity 类 | 注解使用方式、字段命名转换、基类继承、审计字段处理 |
| Mapper/Repository | 同仓库现有的 Mapper/Repository | MyBatis XML vs 注解、自定义查询方法的命名模式、分页实现 |
| Service | 同仓库现有的 Service 类 | 事务注解用法、异常抛出方式、依赖注入风格（构造器 vs @Autowired） |
| Controller | 同仓库现有的 Controller 类 | 统一返回值包装、参数校验注解、权限注解、Swagger 注解风格 |
| 前端 API 层 | 同项目现有的 API 文件 | axios 封装方式、请求/响应拦截、错误处理 |
| 前端页面 | 同项目现有的列表页/表单页 | 组件库用法、状态管理方式、搜索条件布局 |

**风格学习的产出是一份隐式的"编码清单"**——不需要输出给用户，但在 Phase 2 生成每一行代码时都要遵循。比如：
- "这个项目的 Controller 都用 `@RestController` + `@RequestMapping`，不用 `@Controller` + `@ResponseBody`"
- "Service 层的异常统一用 `throw new BusinessException(ErrorCode.XXX)` 而不是返回 error code"
- "所有查询方法都叫 `listXxx`/`getXxx`，不叫 `queryXxx`/`findXxx`"

#### 0.5 输入一致性 Gate（写代码前必做）

按 conventions Section 7.5 检查 tech-design、PRD、原型、coding-knowledge 与当前源码：

1. tech-design 引用的 PRD 版本必须与当前 PRD frontmatter 一致；不一致时停止并要求先更新技术方案。
2. tech-design 必须包含自身 `version` 且 `status: approved`；draft 或未标版本的方案停止实施。
3. 前端需求中，tech-design 记录的 `prototype_prd_version` 必须与当前 PRD 一致；缺失或过期时停止实施。
4. tech-design 中所有现有文件、方法、接口和表必须在当前源码/数据库知识中验证；知识库行号只用于定位，不能替代源码。
5. 原型与 PRD 的字段、页面或交互存在未同步差异时，列出冲突；涉及业务行为或接口契约时停止实施。
6. tech-design 存在参数类型、接口范围、DDL 或调用链错误时，必须先修正方案或获得用户明确裁决。

#### 0.6 写入前 Git 基线（必须记录）

对每个目标仓库，在任何编辑前记录仓库路径、HEAD、远端默认分支与 merge-base、`git status --short`、staged diff、unstaged diff和 untracked 文件清单。用户已有改动是保护基线，本次实现不得覆盖或归入自己的变更。生成后以当前状态相对基线的增量计算本次改动；无法可靠区分时停止并请用户处理或缩小范围。

### Phase 1: 生成计划（向用户确认）

**必须在写任何代码之前向用户展示计划并获得确认。**

基于 Phase 0 的分析结果，输出一份结构化的生成计划：

```
## 代码生成计划

### 代码风格参考
- 后端参考：{从 symbols.md 定位到的参考 Controller/Service 文件路径}
- 前端参考：{从现有页面定位到的参考组件路径}
- 编码规范：{coding-knowledge/infra/code-quality.md 中的关键约束}

### 后端（{仓库名}）
| 序号 | 操作 | 文件路径 | 说明 | 对应任务 |
|------|------|----------|------|----------|
| 1 | 新增 | {从 architecture.md 推导的准确包路径}/XxxEntity.java | 新增实体类 | T-01 |
| 2 | 新增 | {包路径}/XxxMapper.java | 新增 Mapper 接口 | T-01 |
| 3 | 修改 | {从 symbols.md 定位的准确文件路径}:L{行号} | 新增方法 createXxx() | T-02 |
| 4 | 新增 | {包路径}/XxxController.java | 新增 CRUD 接口 | T-03 |

### 前端（{仓库名}）
| 序号 | 操作 | 文件路径 | 说明 | 对应任务 |
|------|------|----------|------|----------|
| 1 | 新增 | src/api/xxx.js | API 调用层 | T-05 |
| 2 | 新增 | src/pages/xxx/index.vue | 列表页面（参考 {模块名}交互原型.html 中对应 page-view） | T-05 |
| 3 | 新增 | src/pages/xxx/form.vue | 新增/编辑表单（参考同一原型文件中的表单视图） | T-05 |

### 数据库
- 执行 tech-design 中的 DDL（已参考 database-schema.md 确认风格一致）

### 注意事项
- {需要用户确认的事项}
```

**计划中的文件路径必须是精确路径**——不是猜测的路径，而是从 architecture.md（包结构）和 symbols.md（现有文件位置）推导出的。对于修改现有文件的操作，标注行号。

用户确认后才开始 Phase 2。

### Phase 2: 按依赖顺序生成代码

**生成原则**：按依赖关系从底层到上层生成，确保引用关系正确。每个文件生成后立即写入。

#### 后端生成顺序

按 Entity → Mapper/Repository → Service → Controller → 配置/其他 的顺序：

**1. Entity/Model 层**

- 根据 tech-design 的 DDL 生成实体类
- **从 Phase 0.4 学到的模式**：字段注解方式（JPA `@Column` 还是 MyBatis-Plus `@TableField`）、基类继承（是否有 `BaseEntity`）、审计字段（`createTime`/`updateTime` 如何处理）、逻辑删除字段
- **从 database-schema.md 参考**：字段命名转换规则（数据库 `create_time` → Java `createTime` 的具体方式，有些项目用 `@TableField("create_time")`，有些靠全局配置自动转换）

**2. Mapper/Repository 层**

- 根据 Entity 生成对应的数据访问接口
- **从 Phase 0.4 学到的模式**：MyBatis XML vs 注解、是否继承 `BaseMapper<T>`、自定义查询方法的命名规则、分页的实现方式（PageHelper？MyBatis-Plus IPage？）
- 包含 tech-design 中提到的自定义查询方法

**3. Service 层**

- 实现业务逻辑，对应 tech-design 中每个接口的处理流程
- **从 Phase 0.4 学到的模式**：事务注解用法（`@Transactional` 的传播级别习惯）、异常处理方式（自定义 BusinessException？统一 ErrorCode 枚举？）、依赖注入风格（构造器注入 vs `@Autowired`）、日志打印习惯
- **从 PRD 验收标准推导校验逻辑**：每个验收条件对应一个校验分支
- **跨服务调用**：从 call-chains.md 中找到项目实际使用的调用方式，照搬其代码模式（而不是自己发明一种新的调用方式）

**4. Controller 层**

- 接口路径、参数、响应结构严格按照 tech-design 的接口设计
- **从 Phase 0.4 学到的模式**：统一返回值包装类（`Result<T>`？`ResponseEntity<T>`？）、参数校验注解（`@Valid` + JSR 303 还是手动校验）、权限注解（`@PreAuthorize`？自定义 `@Permission`？）、Swagger/OpenAPI 注解风格
- 错误码使用 tech-design 定义的业务错误码

**5. 配置/其他**

- MQ Consumer/Producer（如 tech-design 涉及）——从 call-chains.md 中找到现有 MQ 代码的写法
- 菜单/权限配置文件（如需要）
- 新增的常量/枚举类

#### 前端生成顺序

按 API 调用层 → 路由配置 → 页面组件 的顺序：

**1. API 调用层**

- 根据 tech-design 的接口清单生成 API 方法
- **从 Phase 0.4 学到的模式**：axios 封装方式（统一 request 函数？各 API 独立文件？）、请求/响应拦截处理
- 方法名和参数名与 tech-design 的接口编号对应

**2. 路由配置**

- 新增页面的路由注册
- 参考现有路由文件的组织方式

**3. 页面组件**

- **参考 {模块名}交互原型.html 的页面结构**：原型中的表格列顺序、搜索条件布局、弹窗结构直接指导组件代码
- 使用项目实际技术栈的组件库（从 coding-knowledge 或 package.json 确定是 Element UI / Ant Design / 自研组件等）
- 表格列定义从 tech-design 的接口响应字段推导
- 表单字段和校验规则从 tech-design 的接口请求参数推导

#### 每个文件的生成流程

1. 如果是**新增文件**：
   - 确认目标目录存在
   - 使用当前环境允许的文件编辑工具创建
2. 如果是**修改文件**：
   - 先读取完整文件内容
   - 精确修改（不重新格式化周边代码）
3. 生成后立即写入文件系统（不攒到最后一起写）

### Phase 2.5: 验证闭环（必须执行）

代码生成后，按受影响仓库逐一验证：

1. **实际变更核对**：读取 `git status --short` 和相关 diff，确认新增、修改、删除文件与已确认计划一致；未跟踪文件也必须纳入。
2. **任务覆盖核对**：逐项对照 T-XX、API-XX、F-XX 和验收标准，记录代码位置与对应测试；不能仅凭文件存在判定覆盖。
3. **最小相关测试**：优先运行受影响模块的单元测试、类型检查和 lint；无法确定命令时从项目脚本、CI 配置和 README 查找。
4. **构建验证**：运行受影响模块的编译或构建命令。跨仓库变更分别验证，并按依赖顺序执行。
5. **失败处理**：代码问题导致的失败立即修复并重跑；环境或既有失败需保留原始命令、关键错误和未验证范围，不得标记为通过。
6. **范围保护**：若测试或格式化工具产生计划外文件变更，停止并报告，不擅自清理用户已有改动。

### Phase 3: 生成报告

生成前读取 `references/code-gen-report-template.md`，输出 `requirements/{模块名}/{模块名}代码生成报告.md`。记录上游路径与版本、仓库和知识基线、实际文件变更、需求覆盖、未覆盖项与验证结果。

### Phase 4: 输出总结

生成完成后告知用户：
1. 代码生成报告位置
2. 新增/修改的文件数量（按仓库统计）
3. 对应的 tech-design 任务覆盖情况
4. 需要手动处理的事项
5. 测试、构建和实际 diff 核对结果
6. 建议使用 `code-review` skill 审查生成的代码

## 输出目录

输出到 `requirements/{模块名}/{模块名}代码生成报告.md`（完整目录结构见 conventions Section 5）。实际代码变更直接写入目标仓库目录（不在 requirements/ 下）。

## 与其他 skill 的关系

- 前置为已确认的 tech-design、PRD 与适用的原型，后续可使用 code-review 检查实现。
- API-XX、T-XX 与 F-XX 用于关联接口、任务和验收要求；知识库索引用于定位，具体实现以当前源码为准。

## 存量修改 vs 新增功能

AI 根据 tech-design 的改动范围自动判断每个文件是"修改现有代码"还是"新增文件"，并采用不同的生成策略。

### 修改现有代码时的铁律

**只改需要改的，不动不该动的。** 这是存量修改中最常见也最严重的问题——AI 读懂了现有代码后，"顺手"重构了周边逻辑，结果引入了回归 bug。

具体要求：
- **先 Read 完整现有文件**，理解上下文后再动手
- **精确修改**，不整篇覆盖现有文件
- **不重命名现有变量/方法**，即使觉得命名不好——那是另一个需求
- **不调整现有代码格式**（缩进、空行、import 顺序），除非是你新增代码直接相邻的部分
- **不"优化"现有逻辑**——如果 tech-design 说"在 createOrder 方法中新增一个校验"，就只加校验，不改 createOrder 的其他逻辑
- **新增方法时注意插入位置**：按项目现有的方法排列习惯（如 CRUD 顺序、public 在前 private 在后），插入到合理位置

### 判断标准

| 信号 | 判断 | 生成策略 |
|------|------|---------|
| tech-design 标注"修改：XxxService:L120" | 修改现有 | Read → Edit 精确修改 |
| tech-design 标注"新增：{包路径}/XxxController.java" | 新增文件 | Write 完整文件 |
| tech-design 标注"新增方法 createXxx()" | 在现有文件中新增 | Read → Edit 在合适位置插入 |

## 生成原则

- 按已确认的技术方案实现接口与业务规则，遇到上游冲突先处理；校验对应 PRD 验收标准，避免空方法或未完成的业务实现。
- 从项目现有实现学习代码模式；生成前核对模块职责边界，不把明确不属于该服务的逻辑放进去。
- 保留前文的存量修改规则，按依赖顺序逐文件写入；测试、构建及实际 diff 的证据按 Phase 2.5 记录。
- 无知识库时从当前源码、项目指引和同类型实现获取依据；不以缺少索引作为忽略现有规范的理由。
