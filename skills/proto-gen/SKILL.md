## 产物路径解析

在文件查找、新建／修改判定和质量门禁之前，先读取 `../conventions/SKILL.md` 第 5.1 节。新建产物使用中文标准名称，评审报告、代码审查报告与交互原型直接放在 `requirements/{模块名}/` 下；既有文件沿用解析后的实际路径。正文和模板中的标准路径均受该兼容规则约束，下游引用记录实际读取文件及版本。

## Purpose

根据 PRD 与现有前端风格，生成包含全部页面视图的单文件 HTML 原型，并验证关键交互。

## 输入

- PRD 文件路径（Markdown 格式，通常是 `prd-draft` 或手写的 PRD 终稿）
- 项目前端代码（用于提取组件样式，非必须）

## 工作流程

### Step 1: 分析 PRD 和前端代码

1. **读取 PRD**：提取以下信息：
   - 功能清单（每个功能对应的页面）
   - 业务流程图（页面间的跳转关系）
   - 需求详情（每个页面的交互说明、表单字段、表格列）
   - 角色权限（不同角色看到的内容差异）
   - 各 F-XX 内的数据定义和字段配置（表单字段的类型、枚举值、约束）

   **质量门禁**：
   - 提取 PRD 路径、`version`、`module`、`mode`
   - `mode: standard` 时读取 `{模块名}需求评审报告.md`，确认报告检查的是当前 PRD 版本且阻塞问题为 0；报告缺失、版本过期或有阻塞时停止生成并提示先完成评审
   - `mode: mini` 可不要求完整评审报告，但要检查每个 F-XX 是否包含足以支持原型的字段和交互；不足时按下方交互完整性检查处理

2. **读取前端代码**（如果存在）：
   - 查找项目中的前端代码目录（通常是 `src/`、`frontend/`、`web/` 等）
   - 读取全局样式文件（如 `variables.css`、`theme.less`、`tailwind.config.js`）提取：
     - 主色调、辅助色
     - 字号体系
     - 间距体系
     - 圆角、阴影等视觉参数
   - 读取常用组件样式（表格、表单、弹窗、按钮、搜索栏、分页器）提取：
     - 表格的表头样式、行高、斑马纹
     - 表单的标签对齐方式、输入框样式
     - 弹窗的宽度、标题栏样式
     - 按钮的颜色、大小层级
   - 如果使用了 UI 框架（Ant Design、Element UI 等），记录框架名和版本，在生成样式时参考其默认风格

3. **如果没有前端代码**：使用中性的 B 端默认风格（类似 Ant Design 默认主题），不会影响原型的生成。

4. **交互完整性检查**：逐个扫描 PRD 需求详情中每个 F-XX 的交互说明，判断是否足够支撑原型生成。如果某个功能的交互描述缺失或过于模糊（如只有一句"支持批量导出"但没说交互形式），列出来让用户决定：

```
⚠️ 以下功能的交互描述不够详细，可能影响原型准确性：

| 功能 | 当前描述 | 缺少的信息 |
|------|----------|-----------|
| F-03 批量导出 | "支持批量导出" | 触发方式（按钮/菜单）、格式选择（弹窗/直接下载）、进度反馈 |
| F-05 审核 | "提交后进入审核流程" | 审核页面布局、通过/驳回的交互、驳回原因输入方式 |

可以选择：
1. 先补充这些交互细节，我再生成原型
2. 先按常见 B 端做法生成，后续再调整
```

   用户选择补充时，等补充完再继续。用户选择按默认生成时，在对应页面中按常见 B 端交互模式处理，并在 Step 5 输出总结中标注哪些页面使用了默认交互。

5. **规划页面列表**：基于 PRD 功能清单，列出需要生成的页面视图：

```
📋 页面规划：

| 页面视图 | 类型 | 对应功能 | 视图 ID |
|----------|------|----------|---------|
| {导航首页} | index | 概览 | index |
| {列表页} | table | F-01 | list |
| {详情页} | detail | F-02 | detail |
| {新建/编辑} | form | F-03 | form |
| ... | ... | ... | ... |

共 X 个页面视图，全部合并到一个 HTML 文件中，确认后开始生成。
```

### Step 2: 生成单文件 HTML

生成一个自包含的 HTML 文件，所有内容（CSS、多页面视图、JS）内联在同一个文件中。

HTML 顶部注释中记录来源：PRD 绝对/项目相对路径、PRD 版本、生成时间、review 报告路径与状态（mini 模式注明不适用）。

完整的 CSS 变量定义和组件样式参考见 `references/style-templates.md`。

**文件结构**：
1. `<style>` 块：内联全部 CSS（CSS 变量 + 组件样式 + 页面特有样式）
2. `<body>` 中的 `.layout` 布局：`.sidebar` + `.main`
3. `.main` 中每个页面作为一个 `<div class="page-view" id="page-{viewId}">`，同时只显示一个
4. `<script>` 块：页面切换逻辑 `showPage(viewId)` + 交互效果

**布局规则（必须遵守）**：
- HTML 结构必须是 `.layout > .sidebar + .main`，`.main` 内包含多个 `.page-view`
- 每个 `.page-view` 内部结构为 `.header + .content`
- `.main` 用 `flex: 1; min-width: 0` 撑满剩余空间，**禁止设置 max-width 或固定宽度**
- `.page-view` 默认 `display: none`，当前激活的用 `display: flex; flex-direction: column; height: 100vh`（减去 sidebar 后的全高）
- 内容区卡片也应 `width: 100%`

**侧边栏导航**：
- 导航项使用 `onclick="showPage('viewId')"` 而非 `href` 链接
- 当前页面的导航项添加 `.active` 类高亮
- `showPage()` 函数负责：隐藏所有 `.page-view` → 显示目标视图 → 更新侧边栏高亮 → 更新页面标题（含快速跳转栏）

**快速跳转栏（header 右侧）**：
- 每个页面的 `.header` 采用 `justify-content: space-between`，左侧放面包屑/标题，右侧放快速跳转栏
- 快速跳转栏是一排药丸按钮（`.quick-nav`），列出所有功能页面（如"F-01 创建任务"、"F-02 任务列表"），点击直接 `showPage()` 切换
- 当前页面的按钮高亮（`.qn-active`），其他页面为浅灰底色
- `showPage()` 更新 header 时同时渲染快速跳转栏并高亮当前项
- 按钮文案格式为 `F-XX 页面名`，让评审人员一眼看到功能编号对应的页面

**页面视图**：
- 每个页面视图是一个 `<div class="page-view" id="page-{viewId}">`
- 包含自己的 `.header`（面包屑/标题）和 `.content`（页面主体）
- 使用基于 PRD 数据定义和字段配置的真实示例数据
- 包含基本交互效果（弹窗开关、Tab 切换等，纯 JS 实现）
- 弹窗（modal）嵌入在触发它的页面视图中

**导航首页视图（index）**：
- 作为默认显示的第一个页面视图
- 内容区展示：项目名称和模块名称、页面列表卡片（点击调用 `showPage()`）、业务流程概览、角色说明（如 PRD 中有）

### Step 3: 输出结构

```
requirements/{模块名}/
└── {模块名}交互原型.html      ← 单文件原型（所有页面 + CSS + JS），文件名由需求名称与“交互原型”直接连写
```

### Step 4: 浏览器验证与视觉 QA

生成后必须在浏览器中验证，不以“文件已生成”作为完成标准：

1. 打开本地 HTML，检查页面能正常加载且控制台无 JavaScript 错误。
2. 逐个侧边栏和快速跳转入口切换，确认目标视图显示、其他视图隐藏、高亮和标题同步更新。
3. 操作每个关键弹窗、Tab、展开区和确认/取消按钮，确认状态可恢复且不存在死链。
4. 至少检查桌面宽度 1440×900；PRD 明确需要小屏使用时再检查 390×844。
5. 截图进行视觉检查：内容是否溢出、遮挡、截断，表格和表单是否对齐，弹窗是否位于可视区域。
6. 检查离线性：HTML 不引用 CDN、远程字体、远程脚本或远程样式。
7. 发现问题立即修改并重跑对应检查，直到通过；无法运行浏览器时在总结中明确列出未验证项，不能声称已完成视觉 QA。

### Step 5: 输出总结

生成完成后告知用户：
1. 原型文件位置
2. 共包含多少个页面视图
3. 如何查看：`open requirements/{模块名}/{模块名}交互原型.html`
4. 如何微调：
   - 调整全局风格：修改文件顶部 `<style>` 中的 CSS 变量（`:root { ... }`）
   - 调整单个页面：找到对应的 `<div class="page-view" id="page-xxx">` 修改其内容
5. 样式参考来源（从前端代码提取 / 使用默认风格）
6. 浏览器验证结果（页面数、关键交互数、检查视口、控制台错误数）

## 原型修改模式

当用户要求修改已有原型（而非首次生成）时，进入修改模式。

### 触发条件

- 用户要求修改已有原型的某个页面（如"把列表页加一个时间筛选"、"详情页多一个审核记录 Tab"）
- `requirements/{模块名}/{模块名}交互原型.html` 已存在

### 执行修改

直接修改 `{模块名}交互原型.html` 中对应的 `<div class="page-view">` 区块。如需新增页面视图，追加新的 `page-view` div 并在侧边栏导航中添加对应菜单项。

### 输出交互变更摘要

修改完成后，对比本次变更与 PRD 中对应功能的描述，输出交互变更摘要：

```
📋 交互变更摘要（相对 PRD 的差异）

| 页面视图 | 变更内容 | 对应功能 | PRD 影响 |
|----------|----------|----------|----------|
| list | 搜索栏新增"时间范围"筛选 | F-01 | 需求详情需补充筛选条件 |
| detail | 新增"审核记录" Tab | F-02 | 需求详情需补充 Tab 描述 |

💡 建议将以上变更同步到 PRD：告诉我"更新 PRD"即可进入 prd-draft 修改模式
```

**摘要规则**：
- 只列出与 PRD 有差异的变更。如果修改只是调整样式或修复布局问题，不影响 PRD 内容的，不需要列入摘要
- "PRD 影响"列要具体到 PRD 的哪个位置（如"需求详情 F-01 需补充筛选条件"、"F-02 数据定义需新增字段"）
- 用户选择"更新 PRD"时，这份摘要直接作为 prd-draft 修改模式的输入

## 生成原则

- 字段、数据示例、业务规则和交互以 PRD 为准，组件风格参考现有前端。
- 单文件包含全部 HTML/CSS/JS，使用统一样式变量；不依赖 CDN、远程字体或业务 API。
- 提供表达方案所需的页面切换、弹窗和状态反馈，按 Step 4 验证；无法验证的项目明确列出。

## 与其他 skill 的关系

- **前置**：`prd-draft` 或 `prd-review` 产出的 PRD 终稿
- **反向**：原型修改模式输出的交互变更摘要，可作为 `prd-draft` 修改模式的输入
- **辅助**：`coding-knowledge/business/system-overview.md` 的"运营后台交互模式"章节提供现有交互模式参考
